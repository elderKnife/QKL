# 实验完成情况与下一步说明

## 1. 我设计这个实验的科研目的

博士课题需要回答两个基础问题：

1. 分布式能源设备产生的运行数据，能不能用一条真实的联盟链做到“可信存证”，让第三方不用信任某个中心服务器就能核验数据摘要。
2. 电网下发的调控指令，能不能做到“可信追溯”，让接收方核验指令确实来自 GRID、且某批指令确实在链上登记过。

所以这一轮先做最小可行实验，目标是证明技术路线真实跑通、证据可以复现，而不是做性能测试或生产级系统。

## 2. 实验 A 与实验 B 分别验证什么

实验 A（运行数据可信存证）验证：EDGE 生成光伏、储能运行数据后，VPP_A 把整批数据的 Merkle 根写到链上，GRID 从另一个节点读取并重算根，证明“这批数据当时被存证过”，并且任何一条数据被改动都能被发现。

实验 B（调控指令可信追溯）验证：GRID 用独立的业务密钥对指令签名，再把整批指令的 Merkle 根写到链上；VPP_A 核验签名后写入一条关联原批次的转发记录；EDGE 核验签名、Merkle 证明和链上关联关系，最后模拟执行。它证明“指令来源可核验、链上可追溯”，但不等同于设备已经物理执行。

## 3. 原始 JSON 如何变成哈希和 Merkle 根

整个过程可以用一条流水线理解：

```text
原始 JSON
  -> 确定性 JSON 序列化（键排序、无多余空格）
  -> UTF-8 字节
  -> SHA256(叶子域前缀 + 字节)  得到叶子哈希
  -> SHA256(节点域前缀 + 左叶子 + 右叶子)  逐层合并
  -> 批次 Merkle 根
```

域前缀是为了防止“叶子”和“父节点”结构混淆。排序规则、左右顺序、奇数叶子的处理都固定下来，任何人重算都会得到同一个根。

## 4. 哪些信息上链，哪些信息不上链

上链的只有关键摘要和元数据：

- batchId（批次编号）
- evidenceType（证据类型）
- dataType（数据类型）
- merkleRoot（Merkle 根）
- recordCount（记录条数）
- submitter（提交方）
- relatedBatchId（关联批次，用于转发记录）
- timestamp（时间戳）

不上链的包括：

- 原始业务 JSON
- 每条数据的 SHA-256 和 Merkle 证明
- 实验 B 的指令数字签名

这样设计的原因是：链上只保存无法被悄悄替换的小段摘要，原始数据和证明放在链下，既省链上存储，也保护业务数据。

## 5. FISCO BCOS 五节点承担什么作用

五个节点 GRID、VPP_A、VPP_B、THIRD_A、THIRD_B 组成 `group0`，用 PBFT 共识共同确认交易。它们的作用不是“谁的数据存在谁那里”，而是：

- 每个节点都保存同一份账本副本；
- 一笔交易要经过共识确认才会被打包进区块；
- 从不同节点查询应该得到相同结果，这也是实验里从 20200 和 20202 两个 RPC 端口重复查询的原因。

## 6. 当前是否达到可以向导师汇报的程度

达到“最小可行性验证”的汇报程度。真实交易成功、回执 status=0、两个实验的 Merkle 根都已上链、跨节点查询一致、成员证明通过、篡改实验显示验证失败。这些都有真实交易哈希、区块号、合约地址和输出文件可查。

但还不足以汇报“系统可投入生产”或“性能可支撑实际电网规模”，因为本轮没有做性能、并发、容错和安全性评估。

## 7. 目前技术方案还有什么局限性

- 没有做吞吐、延迟、并发和容错测试，不能说明系统性能；
- 原始 JSON、单条哈希和 Merkle 证明保存在链下，链下文件需要配套保存和防篡改方案；
- Merkle 成员证明只能证明“某条记录属于某个摘要批次”，不能代替数据本身真实性的线下核验；
- 摘要存证不能等同于设备已经实际执行指令，转发记录只是链上关联转发，不是物理执行证明；
- 实验 B 的业务密钥仅用于演示来源签名，没有证书体系、密钥轮换或权限管理；
- 当前只有一条链、一个群组、五个节点，没有做跨群组、跨链或更大规模网络实验。

## 8. 本轮验收结论

依据 [验收报告.md](验收报告.md) 和只读链上复核，实验 A 与实验 B 的核心验收项全部通过，没有发现需要重做链上交易的证据缺口。下一步如果继续推进，建议优先补充链下数据归档方案和业务密钥管理体系，再逐步开展性能与容错实验。
