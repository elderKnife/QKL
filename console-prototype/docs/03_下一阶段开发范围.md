# 下一阶段开发范围与验收建议
以下是交接目标与建议，不表示这些模块已经实现，也不替代导师确认后的正式任务书。

## 已提出的目标
- 10 个逻辑边缘节点，每节点 30 台设备：光伏逆变器、储能设备、充电桩各 10 台，共 300 台。
- 上行：边缘汇聚并签名，VPP 验签后构建 Merkle 批次并存证，GRID 独立核验。
- 下行：GRID 签名并存证，VPP 核验转发，边缘独立核验后模拟分发。
- 一条指令对应一个存证批次；是否另建转发证据批次需要明确。
- GRID/VPP 使用独立数据库，通过 HTTP API 交换数据。
- 优先摸底万条数据完整性验证和百条指令验证；现阶段没有已验证性能指标。

## 建议开发顺序
1. 固定协议：schema、协议版本、数值/单位/时间、ID、批次边界、签名范围、Merkle 算法和证明结构。
2. 修复 P0/P1 核心问题，完成纯本地正确性检查和逐条异常定位。
3. 建立 GRID/VPP 独立数据库、API、持久化状态与幂等键；角色账户及可信公钥独立置备。
4. 实现逻辑边缘节点、设备归属校验、上行签名、下行独立验证与模拟反馈。
5. 在独立测试链集成链适配器、结构化回执和超时恢复；补充版本及部署证据。
6. 协议和验收口径确定后，再设计万条数据/百条指令的规模验证及性能测量。

## 建议正确性验收项
逐条输出 recordId/commandId、批次、验证阶段、通过/失败、错误原因及相关交易/证明引用，避免只给汇总 pass。
覆盖正常、内容篡改、缺失/重复 ID、空批次、非法数值、非法签名、公钥不可信、错误根/位置/路径、重放、过期及交易未知。
失败验证必须阻止后续转发和模拟成功反馈；重试不得导致重复消费。
每个链上提交保存回执状态、实际发送方/合约、交易哈希、回执高度和批次查询结果；逐条报告与汇总结论一致。
模拟反馈只能称为模拟结果，不作为设备实际物理执行证明。

## 仍需导师确认
- 万条数据的批次数、每批大小、是否要求全量成员证明。
- 签名是否纳入叶子，边缘签名覆盖内容，密钥登记/轮换/撤销方式。
- nonce 有效期、顺序与消费语义，部分分发失败和链超时的恢复规则。
- 数据库/API 的部署分工、鉴权及证据保存期限。
