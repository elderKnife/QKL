# 02 架构设计

## 1. 角色与身份边界

任务书特别强调“边缘节点、设备、业务主体、交易账户、Web 用户和 PBFT 共识节点不是同一种身份”。
本实验的身份划分如下：

| 身份 | 数量 | 持有物 | 用途 |
|---|---|---|---|
| 边缘业务身份 | 4（edge-01..04） | 各自 PEM 私钥 | 对边缘包、回执做 ECDSA 签名；**没有链账户** |
| VPP 业务身份 | 2（vpp-a/b） | 各自 PEM 私钥 | 对批次 envelope 签名（供 GRID 验签） |
| GRID 业务身份 | 1 | PEM 私钥 | 合约 owner |
| 链交易账户 | 3（grid、vpp-a、vpp-b） | 各自 PEM 私钥 | 发交易；VPP A/B 写批次/回执根，GRID 写命令根 |
| PBFT 共识节点 | 5（node0–4） | 节点证书与 node.key | 只负责共识与 RPC，**不是业务主体** |

注意：同一个 VPP 的“业务签名密钥”和“链交易账户”在本实验中恰好使用同一份 PEM
（`config/keys/vpp-a.pem`），这是为了减少样例文件数量；代码中它们是两个独立用途，
换成两把钥匙不需要改协议。

## 4. 为什么“边缘 ↔ VPP 不上链”是结构性的，而不是口头约定

1. `src/edge/service.py` **不导入** `src.chain`、`bcosclient`、`web3` 任何模块；
2. 边缘配置 `config/system.json` 的 `edges[]` 中没有 `chain`、`account` 字段；
3. `tests/test_architecture.py` 在子进程中导入边缘模块后断言 `client.bcosclient`
   与 `src.chain.*` 均未加载；并静态检查源码不含链导入；
4. 边缘进程只有一个外部依赖：`vppUrl`。

因此即使链停机，边缘仍然可以继续收数、签名、上报（只是 VPP 会返回 503），
这与“边缘不因链故障而不可用”的设计目标一致。

## 5. VPP → GRID 的链使用方式

- VPP 只调用合约的 `registerBatch(batchId, root, recordCount, submittedAt, vppId, schemaVersion)`；
- 链上状态只保存 `bytes32 root` 与定位元数据，**不保存 records / proofs / packet**；
- VPP 把 `envelope`（records + proofs + chainReceipt）与自己的业务签名通过 HTTP 发给 GRID；
- GRID 的校验顺序：

  1. 校验 JSON 结构与版本；
  2. 用预登记公钥验证 VPP 签名；
  3. 用**自己的**链客户端（node3）按 `batchId` 读 `getBatch`；
  4. 用离线 records 重算 Merkle 根；
  5. 与链上根、VPP 声明的根三方比对；
  6. 用链上根逐条验证 proof；
  7. 可选：用自己的链客户端按 `txHash` 取回执，核对 `status=0` 与目标合约地址。

只有以上全部通过才返回 `VERIFIED`。

## 5.1 指令下行路径（第二轮新增）

```
grid ── 命令+签名+命令锚定(GRID 交易) ──▶ vpp ── 校验 GRID 签名/链上命令根 ──▶ edge
  ▲                                                                       │
  │                                                                       │ 校验 GRID 签名/目标/有效期，
  │                                                                       │ 执行模拟动作，签名回执
  └── 回执 envelope(含回执锚定) ◀── vpp ◀──────────────────────────────────┘
```

- **GRID 锚定命令**：`batchId = BATCH-CMD-<commandId>`，`root = leaf(命令)`，`schema=GRID-COMMAND-V1`；
- **VPP 校验**：GRID 业务签名 + 链上命令根一致 + 目标边缘归属；
- **边缘校验**：GRID 签名、目标 edge/device、有效期、`commandId` 去重；
- **VPP 锚定回执**：`batchId = BATCH-ACK-<ackId>`，`root = leaf(ack)`，`schema=EDGE-ACK-V1`；
- **GRID 核验**：VPP 签名 + 回执根与命令根都在链上且一致，才标记 `COMPLETED`。

边缘依旧没有链客户端：它对命令的完整性依靠 GRID 签名（签名覆盖命令全部内容），
链上锚定由 VPP 与 GRID 各自独立查询。

## 6. 幂等、重试与失败语义

| 场景 | 行为 |
|---|---|
| 同 packetId、同摘要重复上报 | VPP 返回既有状态（`duplicate: true`），不重复上链 |
| 同 packetId、不同摘要 | 409 `IDEMPOTENCY_CONFLICT`，保留原记录 |
| 同 batchId 链上已存在且根一致 | 视为“重试后已经成功”，恢复为 `CONFIRMED`（`recovered`） |
| 同 batchId 链上已存在但根不同 | `FAILED`，不覆盖 |
| 链不可用/超时 | `CHAIN_UNAVAILABLE`（503，可重试）；不生成假回执 |
| 交易已发出但回查不到 | `UNKNOWN`（502），不盲目重发 |
| GRID 拒绝 | VPP 记录 `FORWARD_FAILED` 并保留原始 envelope，可人工排查 |

本地状态用 SQLite（每服务一个库）+ 边缘 JSON 状态文件持久化；
边缘重启后 `seenRecordIds` 仍保留，重复编号会被拒绝。

## 8. 关键设计取舍

1. **只有根哈希上链**：链上不保存明细，GRID 必须拿到离线批次才能校验；这也说明
   “链上可查”与“链下原文留存”是两件事，二者缺一不可。
2. **一包一批**：`batchId = BATCH-<packetId>`，天然唯一，便于幂等与回查。
3. **证明跟着批次走**：VPP 一次性构树、一次性导出全部证明，避免逐条重建。
4. **GRID 独立连接**：GRID 用 node3 读取，VPP 用 node1/node2 写入，形成“写入/读取
   不同节点”的交叉验证；证据见 `data/reports/chain-evidence.json`。
5. **业务签名与链账户分离到模块**：没有任何“传入主体名即可代签”的公共接口；
   私钥文件权限强制 0600（`src/common/crypto.py`、`src/chain/keys.py` 都会检查）。
6. **可视化面板是只读旁路**：`src/web` 只调用各服务与链 RPC，不签名、不写库、不发交易；
   它宕机不影响数据链路，也不能改变 GRID 的核验结论（见 `docs/06`）。
