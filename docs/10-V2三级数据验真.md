# V2：30 条 → 300 条 → 12000 条

## 一、拓扑与正常模拟约定

- `vpp-a` 对应 `edge-01`～`edge-10`；`vpp-b` 对应 `edge-11`～`edge-20`；`vpp-c` 对应 `edge-21`～`edge-30`。
- 每边缘 30 台设备：10 台光伏、10 台储能、10 台充电桩，共 900 个全局唯一设备 ID。
- 以模拟必成功为前提；VPP 收齐所属 10 个边缘同一会话/轮次的数据才组批。未收齐不冒充 300 条，不做超时降级、补零或部分组批。
- 自动采集每 30 秒一轮，首次约 2 秒后开始；每 VPP 共用会话 ID 与起始时钟，避免各边缘自行计数造成错批。暂停后的原位恢复继续下一序号；暂停不撤销已经发出的交易。
- 服务重启后暂停，显式恢复后继续；业务会话和不可变原始输入保存在 SQLite。

## 二、分层流程和标识

边缘：生成 30 条记录 → 计算根 → 签名数据包 → 根写链 → 查询合约确认匹配根与实际发布者 → 停止上链计时 → 补查可用回执 → HTTP 发送数据包、签名与链定位信息给 VPP。

VPP：验证已登记的边缘公钥、归属及 30 台设备名单 → 对原始数据重算根 → 以独立链客户端查询该批根和实际发布者 → 查询交易回执，核对合约、发送者、成功状态和 `BatchRegistered` 事件 → 保存原始数据与验真结果。收齐同一轮的 10 包后，以完整 300 条记录构树；VPP 签名并提交自己的根，查询合约确认已提交的匹配状态后停止计时，补查可用回执，再将原始数据直传 GRID。

GRID：验证 VPP 签名和所属 300 台设备名单 → 重算该 300 条树 → 独立查询链根、发布账户和交易回执并比对 → 自动验真成功后保存自己的原始副本。每批自动校验不会替代后续 40 批全量重算。

| 对象 | ID | 数量 | 链上协议 |
|---|---|---:|---|
| 边缘包 | `packetId=PKT2-<随机值>`，链批次 `E2-<packetId>` | 30 | `EDGE-ROOT-V2` |
| VPP 业务批次 | `V2-<vppId>-<sessionId>-<六位轮次>` | 300 | `VPP-ROOT-V2` |
| VPP 40 批聚合 | `G2-<vppId>-<sessionId>-<五位分组序号>` | 12000 | `VPP-GROUP-ROOT-V2` |

第一组严格为 #1～40，第二组 #41～80，以此类推。不混 VPP、不混会话、不排序替换轮次，不允许重复批次。每个 VPP 独立累计，GRID 筛选 VPP 后只展示其批次。

同一对象 ID 和相同原始输入为幂等重试，不重新模拟数据；相同 ID 携带不同原始输入被拒绝。链上同一批次不允许覆盖。提交结果不明时，用相同 ID 查询恢复；无法确定原交易时标记 `recovered`，新上链时延与回执时延为空，不伪造交易哈希或耗时。

## 三、原始记录与哈希规则

设备记录含：`recordId, deviceId, deviceType, metric, value, unit, timestamp`。指标为 `active_power_kw`，单位 `kW`，数值最多三位小数；光伏和充电桩非负，储能允许正负。UTC 时间精确到毫秒。

每个 30 条包和 300 条业务批次都对**完整原始记录**构建 `MERKLE-V1`：

1. 规范 JSON 使用现有 `CANON-JSON-V1`，按 `(deviceId, timestamp, recordId)` 排列记录。
2. 叶子为 `SHA256(b"FISCO-BCOS-EVIDENCE-LEAF-V1:" + canonical_bytes(record))`。
3. 内部节点为 `SHA256(b"FISCO-BCOS-EVIDENCE-NODE-V1:" + left_raw32 + right_raw32)`。
4. 奇数层的最后一个节点直接提升，不复制；得到 32 字节根，传输以 64 位十六进制表示。

40 批聚合沿连续轮次排列，对每批以下描述符构树：

```json
{"batchId":"...","vppId":"vpp-a","sessionId":"...","sequence":1,"recordCount":300,"rootHash":"64位十六进制"}
```

聚合叶子为 `SHA256(b"QKL-GROUP-LEAF-V2:" + canonical_bytes(descriptor))`，内部节点和奇数提升同上。描述符把根与业务批次、主体、会话和顺序绑定，避免相同根被替换到其他批次。聚合根仍只是一个 32 字节根；40 个描述符通过 HTTP 传送，不保存到链上。

GRID 点击「批量校验」时，遍历自己数据库中的 40 个业务批次的**12000 条原始记录**，分别重算 40 个根，用这些新根和对应批次元数据构建第二层树，然后从链读取聚合根比对。不会直接拿已保存的 40 个根代替对原始数据重算。检查发现某批异常后继续检查其余批次；返回失败批次清单。链不可用为 `ERROR`，内容不匹配为 `FAIL`，全部一致为 `PASS`。

## 四、合约和交易回执

新合约 `RootHashRegistryV2` 保留旧查询的六字段布局，但将 `subjectId` 绑定 `msg.sender`；另可通过 `getPublisher(batchId)` 取得实际交易发布者。GRID 和 VPP 都核对真实发布地址，不能仅相信 HTTP 中的 `vppId`。

```text
authorizeSubject(account, subjectId)      // 部署者登记，账户只能绑定一次
registerBatch(batchId, root, recordCount, submittedAt, subjectId, schemaVersion)
getBatch(batchId) -> exists, root, recordCount, submittedAt, subjectId, schemaVersion
getPublisher(batchId) -> publisher
```

业务数据仅根哈希上链，定位元数据随根保存：批次 ID、记录数、毫秒时间戳、主体 ID、协议版本、发布地址。设备原始数值和完整树不写链。`submittedAt` 是客户端声明时间，不作为链共识时间证明。

写入结果包含 `txHash, blockNumber, registryAddress, status, commitLatencyMs, broadcastLatencyMs, receiptLatencyMs, confirmationMethod`。成功上链必须独立查询合约，确认批次根、数量、主体、协议和真实发布地址匹配。停止上链计时后再补查回执；回执可用时继续核对其发送方、合约及 `BatchRegistered` 事件，不可用时以已验证的链状态确认成功，回执状态为 `NOT_AVAILABLE`。原始 FISCO 回执含 `from, to, status, logs`，`status=0x0` 表示执行成功。读链查询不产生新的交易回执。

## 五、时延口径

所有计时均使用后端单调时钟 `perf_counter_ns`，保留未四舍五入的实测数值。2026-11-14 按最新要求调整了主要展示口径：

- **上链确认时延 `commitLatencyMs`**：进入提交临界区后，调用 SDK `sendRawTransaction` 前开始，到查询合约读出匹配的批次根、记录数、主体、协议及实际发布账户时结束。含签名、广播、共识和短间隔读链确认；不含构树、提交前幂等检查、锁排队或之后的回执查询。默认每 20 ms 查询，实际调用时间与查询粒度均包含在结果内。仅 RPC 接收交易不等于成功上链；截止时间仍未读到状态则为 `TX_OUTCOME_UNKNOWN`。这是客户端观察到的确认延迟，并非链内时间戳相减。
- `broadcastLatencyMs`：签名与 RPC 提交至收到交易哈希，独立记录作为参考，不能用该值冒充成功上链耗时。
- `receiptLatencyMs`：新版从同一提交起点到停止上链确认计时后补查取得回执的时间；没有回执则为空。旧版保存的是 SDK 固定 1 秒间隔轮询后取得回执的时间。该字段不再作为主要上链时延，旧历史也不改写为新口径；`timingVersion=CHAIN-STATE-V1` 区分新版。
- VPP `verification.durationMs`：接收边缘包后校验结构、归属、签名、重算和独立读链及可用回执核对；不含后续 300 条组批和转发。
- GRID **300 条自动验真 `verificationMs`** 保留完整流程时间：结构、签名、设备名单、重算、读链和可用回执核对。
- GRID **12000 条手动校验 `comparisonNs` / `comparisonMs`**：先完整重算 40 个根和聚合根，再独立读链；两根都准备好后开始计时，只执行一次 `computed_root == chain_root`，立即停止。页面主要显示 `comparisonNs / 1e6`，单位 **毫秒（ms）**，名称「根比较耗时（仅比较）」。不包含树重算、读链、业务/数据校验或 HTTP 传输；单次比较很短，实测值包含高精度计时本身开销，不代表 12000 条验证的完整处理能力。没有可比较的两根时结果为空，不显示为 0。
- GRID 12000 条 `hashComputeMs`：读取 GRID 原始副本、校验记录并构造 40 个树和聚合树，以及逐批与清单核对；**不计入主要根比较耗时**。
- GRID 12000 条 `chainQueryMs`：独立读取链上聚合根、实际发布者及元数据；根相等比较在此段之后单独计时，**不计入主要根比较耗时**。
- GRID 12000 条 `totalVerificationMs`：完整手动校验总处理时间，含原始数据读取、重算、读链和比对，不含 HTTP 往返和结果落盘；仅在详情展示。

新版手动报告标记 `timingVersion=ROOT-COMPARE-V1`、`primaryTimingScope=ROOT_EQUALITY_ONLY`，其 `verificationMs` 对应 `comparisonMs`；之前历史报告中的 `verificationMs` 是完整耗时，保留原值。前端只用新增 `comparisonNs` 展示主要指标；旧报告没有该字段时显示「尚未按新口径计时」，点击校验后生成新测量，不从旧总耗时推算。每次结果均保存独立历史，`rootsEqual` 返回相等性，`batchChecks` 保存 40 批各自的新根与预期根。

## 六、接口与持久化

边缘服务：`/api/v2/state`、`/api/v2/packets`、`/api/v2/packets/<id>`、`POST /api/v1/collection/{start,pause,tick}`、`POST /api/v2/packets/<id>/retry`。

VPP 服务：`POST /api/v1/edge-packets`、`POST /api/v2/collection/{start,pause,tick}`、`/api/v2/state`、`/api/v2/edge-packets`、`/api/v2/batches`、`/api/v2/groups` 和相应详情。

GRID 服务：`POST /api/v2/batches`、`POST /api/v2/groups`、`POST /api/v2/groups/<id>/verify`、`/api/v2/batches`、`/api/v2/groups`、`/api/v2/vpps/<id>/state`。

VPP 上传业务批次和聚合组成功后，GRID 仅返回 HTTP 204 空响应，不回传根哈希比对结果、耗时或验真报告。GRID 仍完成本地校验并保存原始数据、验证证据，页面通过 GRID 查询接口读取；手动批量校验结果仍返回控制台供展示。VPP 以 HTTP 2xx 记录 `DELIVERED` 和 `delivery.httpStatus`，不解析成功响应的 JSON，不新建 `gridReport`；失败 HTTP 状态仍阻止该批次被记为送达。旧持久化记录中的历史报告不删除。

控制台 `/api/v2/` 将查询代理到相应业务节点，登录后使用；批量校验要求 GRID 角色。端口均只绑定本地 `127.0.0.1`。独立领域 API 为本机实验使用，未建设生产认证/设备接入系统。

原始对象与处理状态分开持久化在 `data/v2/<role>/pipeline.db`。前端列表仅返回摘要，详情按需加载原始数据，避免每 4 秒轮询都传输完整历史。旧 `RootHashRegistry` 和 V1 原始记录保留，不改变其规则或覆盖旧证据。

本次 V2 实现范围是上述上传、验真与采集控制，以及下文新增的 GRID → VPP 指令发布和核验成功返回。V1 指令业务源码保留，新入口采用独立的 V2 指令协议。缺失边缘重试/容灾、多主机网络故障处理、生产密钥管理及数据可用性不是本次成功模拟实验的目标。

## 十二、GRID 指令下发与 VPP 核验成功返回（2026-11-14）

GRID 账户的 WORKSPACE 增加「指令下发」。单条发布选择 VPP、边缘、设备；批量发布每次只选择一个 VPP，可跨其所属边缘选择多个设备并加入发布清单。切换 VPP 会清空清单。后端校验设备归属、重复目标和单 VPP 约束，跨 VPP 请求在上链前拒绝。每个所选设备生成一条模拟 `set_active_power_kw` 指令，参数按类型固定为光伏 10 kW、储能 −5 kW、充电桩 7 kW；不要求用户填写内容。指令仅送到 VPP 验真，不向边缘转发，也不改变设备状态。

每次发布有 `releaseId`，整批有一个 `dispatchId`，每条指令有 `commandId`。整次发布只涉及一个 VPP、一次根上链，批量模式最多 300 台设备，单条模式只允许一个目标。指令内容绑定发布 ID、批次 ID、GRID/VPP、边缘、设备、设备类型、动作、参数和秒级发布时间，`simulation=true`。

- 指令对象：`GRID-COMMAND-V2`；批次：`GRID-COMMAND-BATCH-V2`；规则：`COMMAND-MERKLE-V2/CANON-JSON-V1`。
- 指令按 `commandId` 排序，叶子为 `SHA256(b"QKL-COMMAND-LEAF-V2:" + canonical_bytes(command))`，内部节点沿用 MERKLE-V1 原始 32 字节拼接及节点前缀，奇数节点提升。单条指令即单叶树。
- GRID 用现有 GRID 账户把 `dispatchId`、根、数量、提交时间、`grid` 主体及新协议版本写入现有 `RootHashRegistryV2`；合约和设备数据上传协议不变。模拟指令、目标清单、成功返回及签名不写链。
- 原文信封与 GRID 业务签名通过 `POST /api/v2/commands` 直传目标 VPP。VPP 校验目标归属、GRID 签名，重算根，独立查询合约根、数量、协议和实际 GRID 发布账户，并比较两根。
- VPP 核验通过后在同一 HTTP 响应直接返回 `VPP-COMMAND-VERIFIED-V2` 成功凭证及 VPP 签名，绑定本次发布/分批/根/数量。GRID 验证签名和这些字段后才标记 VERIFIED；仅 HTTP 200 不代表核验成功。此凭证表示指令内容核验通过，不表示设备执行。
- 本次 VPP 核验通过标记 VERIFIED，并给出 `allVerifiedAt`；失败标记 ERROR，不给出成功时间。原始指令、链存证、成功凭证及结果分别持久化在 GRID 和目标 VPP 的 V2 数据库。先前跨 VPP 的实验历史保留可查看，不再创建此类发布。

时间显示：指令 `issuedAt` 为 UTC 秒级，页面按北京时间显示到秒。`receivedAt` 是 GRID 完整收到 VPP HTTP 响应的本地毫秒时间，只有返回内容和签名通过检查才作为成功时间保存；`allVerifiedAt` 为全部成功时的最后接收时间。普通设备上传时间戳仍统一显示到秒。

耗时均为后端单调时钟实测、单位 ms，分别展示：

- `receipt.verificationMs`：与 `receipt.comparisonMs` 相同，只计最终两个根相等比较；由 `comparisonNs` 除以 1e6，页面保留 6 位小数。重算、验签、读链和传输均不计入，与数据批量校验口径一致。
- `receipt.totalVerificationMs`：VPP 从开始处理到验签、归属校验、重算、独立读链和根比较完成；不含成功凭证签名、落盘、网络返回。仅在详情展开查看，不作为主要验证耗时。
- 新凭证标记 `timingVersion=ROOT-COMPARE-V1`、`primaryTimingScope=ROOT_EQUALITY_ONLY`，发布摘要同步保存比较耗时；旧凭证不改写，查看历史时根据原有 `comparisonNs` 展示仅比较耗时，完整耗时沿用原值。
- `chainAnchor.commitLatencyMs`：沿用数据上传的成功上链确认口径。
- `deliveryMs`：GRID 发起 HTTP 下发到完整收到响应，含 VPP 处理和返回；不含 GRID 随后的响应验签。
- `publishToReceiptMs`：GRID 通过目标检查、开始本次发布到完整收到 VPP 响应，含指令生成、签名、落盘、上链和投递；不含 GRID 随后的响应验签，只有签名核验通过才保存为成功接收耗时。
- `publicationTotalMs`：本次发布通过目标检查后开始，含生成、签名、落盘、上链/投递及 GRID 检查成功凭证，结束于处理完成；在详情展开查看，与主要根比较耗时分开。

新增 GRID API：`GET /api/v2/command-targets`、`POST/GET /api/v2/commands`、`GET /api/v2/commands/<releaseId>`。控制台对应 `/api/v2/grid/` 路径，发布要求 GRID 角色，VPP 账户不显示发布入口且 POST 被拒绝。设备上传接口继续成功返回 HTTP 204 空响应，不接收 GRID 验真报告。
